# Windows Torch consumer rebuild for libuv 1.53 — design investigation

2026-10-29. Scope: read-only source investigation and new assessment artifacts only. No compiler/toolchain invocation, install, C/C++ patch, Torch import, DLL load or runtime replacement. The route is technically plausible but **not validated or approved for production**.

## Decision

Unmodified libuv 1.53 requires rebuilding its Windows Torch consumers against its own headers and import library. A DLL swap into the installed `2.14.0+cpu` wheel is blocked by the recovered layout: old embedded loop 464 bytes versus new 472 bytes. Matching the new DLL to MSVC/UCRT alone does not remove the extra source-declared field. See prior exact-header REPORT (input receipt below).

A single .cpp may be compiled to an object as part of a valid incremental build, but that object is not an independently replaceable Torch component. Exact commit `08187d9e0fba026dc8217405802ab5381dc88d90` puts TCPStoreLibUvBackend.cpp in `libtorch_distributed_base_sources` (build_variables.bzl:516,539); caffe2/CMakeLists.txt:588 appends that list to TORCH_SRCS, :761 merges TORCH_SRCS into Caffe2_CPU_SRCS, and :846 creates torch_cpu. The consumer therefore must at least be recompiled and **torch_cpu relinked** with a coherent build graph, generated headers, macros, exports and dependencies. Private class layout and intrinsics cannot be injected by compiling an extension. This does not prove every Torch source object must change; it establishes why an isolated cpp/DLL patch is not a deliverable.

For a maintainable replacement, build a complete CPU wheel from the exact source commit and pinned submodules, with new libuv headers/import library/DLL from one build prefix; package and test its native closure (`torch_cpu`, c10, torch, Python binding artifacts, bundled dependencies, headers and metadata as emitted by the official build). Do not transplant a newly linked torch_cpu into the old wheel without a separately evidenced mixed-build ABI/CRT audit. Existing torchvision/torchaudio/custom native extensions, if installed, need inventory and compatibility tests and potentially matching rebuilds; their mere presence or need to rebuild was not established here. Other processes embedding libuv structs must be identified independently; this Torch rebuild does not repair every uv.dll consumer.

## Source facts and toolchain constraints

- Same-commit official `.ci/pytorch/windows/build_install_deps.py` fetches libuv 1.40.0; it must not silently run unchanged for the 1.53 candidate. Prior receipt maps this archive's DLL bytes to the installed original, but lacks full wheel build attestation. The old package recipe says VS2017/VC14.1; that is **not** proof of Torch's compiler or an instruction to rebuild modern Torch with VS2017.
- Same-commit build_env_setup.py declares `VC_YEAR` 2022 or 2019, defaults 2022 (:417), selects VS version ranges [17,18) or [16,17), and captures `vcvarsall x64` environment. CPU profile sets USE_CUDA=0 (:52); official wheel uses `python -m build --wheel --no-isolation`. pyproject.toml:24 uses scikit-build-core and :77 forces Ninja on Windows. Build requirements are ranges, not a reproducibility lock; CI-pinned dependency versions and exact Python ABI still need recovery and freezing.
- Top-level CMakeLists.txt:83 requires C++20 (C17 for C); :662 explicitly rewrites /MD and /MT according to CAFFE2_USE_MSVC_STATIC_RUNTIME. The option's default alone does not attest the installed wheel's effective CRT. Candidate build must capture actual compiler/link commands, CMake cache, architecture, SDK version, runtime mode, release/debug setting, exports and PE imports. Keep all libraries sharing CRT-owned resources consistent; never assume MinGW/MSVCRT and MSVC/UCRT interchangeable.
- README contains older Windows VS2017/2019 generator prose, while exact current wheel scripts/pyproject use Ninja and default VS2022. This documentation inconsistency is recorded; do not use the older paragraph as evidence of modern wheel toolchain support. No exact installed-wheel MSVC patch version or Windows SDK attestation was recovered.
- Parent supplied current machine inventory (not independently measured here): MSVC 14.50.35717 under D:/Microsoft Visual Studio, bundled CMake, SDK 10.0.26100.0, 20 logical processors, C free 9.84 GiB and D free 67.08 GiB, physical RAM unknown. cl/cmake/ninja absent from PATH does not mean uninstalled. Presence of this newer MSVC does not establish acceptance by the exact source or its third-party deps. If vswhere reports a newer VS major outside [17,18), official discovery may reject it; verify product version and explicit supported toolset selection before any future build. SDK headers alone do not establish all SDK libraries/tools/components are installed.
- Top-level CMakeLists.txt:494-520 may disable distributed/Gloo when libuv is missing. A successful build with distributed disabled would evade the requested consumer and is a failed route MVP. Inspect configured USE_DISTRIBUTED, USE_GLOO and libuv resolution; retain TORCH_USE_LIBUV and actual header include traces.

## CPU versus GPU

Preserve installed CPU intent explicitly (`USE_CUDA=0`, CPU profile, no XPU/ROCm) and verify final version/config and absence of unintended GPU dependencies. Top-level USE_CUDA defaults ON (:296), so a casual source build is not equivalent to the installed +cpu package. CPU removes CUDA/cuDNN/NVTX/MAGMA and GPU architecture compilation requirements, but retains large CPU kernels, code generation, distributed/Gloo and libuv consumer work. GPU would be a separate scope: CUDA/compiler compatibility matrix, toolkit/cuDNN/NVTX/MAGMA, GPU architectures, more disk/build work, and real GPU tests. Official CPU profile does not need a GPU to demonstrate TCPStore libuv operation.

## Conditional resource assessment

No trustworthy host-specific wall-time estimate is available. README's generic initial-build estimate is not a benchmark for this machine or commit and is not adopted. Budget separately: recursive pinned source/submodules; locked Python/build/BLAS/OpenMP deps; libuv source/build/install prefix; CPU objects/generated code; linker/PDB scratch; staging+wheel+fresh validation environment; logs, original backup and rollback wheel; temporary download/extraction and compiler cache. Peak usage is their overlapping total, not final wheel size.

C's 9.84 GiB is a material scratch/pagefile/cache risk. D's 67.08 GiB cannot be declared sufficient without this inventory and a measured CPU pilot. A future approved build should use explicit D-local TEMP/TMP/cache/source/build/staging prefixes and retain reserve; do not clear other tasks' files. RAM is unknown, so 20 logical CPUs must not be translated into 20 compile workers; bound parallelism after measuring compile/link memory. Exact resource gate is measured free-space reserve, peak RAM/commit and disk growth at configure/codegen/compile/link/package, with abort thresholds agreed before execution. Additional approved storage/build host may be required. No build is recommended on current evidence alone.

## Isolated MVP and acceptance — proposed, not executed

1. Freeze original environment/wheel/DLL hashes, full dependency inventory, Python ABI, native consumer/extension inventory and current application baseline. Use a fresh isolated prefix and source/build tree; preserve production unchanged. Pin exact Torch commit, all submodule revisions, dependency artifacts and libuv 1.53 source/hash. Review security and license provenance.
2. Build libuv with selected MSVC toolset/SDK/CRT and original Windows configuration intent, recording tests, PE exports/imports and runtime mode. Compile separate header-layout probes and prove new consumer header paths, uv_loop_t size/offsets and uv_loop_size agreement. Probe success alone does not prove Torch compatibility.
3. Configure full CPU Torch with explicit libuv_ROOT pointing only to the new prefix; capture include traces, cache, feature flags, link map and artifact hash manifest. Ensure TCPStore object and all discovered libuv consumers rebuild; use clean artifacts to avoid stale old-header objects. Build/package wheel through official backend and inspect the native dependency closure and wheel contents.
4. Only in new subprocesses/isolated environment, import wheel and attest loaded uv.dll path/hash/version, torch version/git/config and distributed availability. Exercise explicit libuv TCPStore server/client in separate processes: set/get/add, multi-client concurrency, wait/timeout, connection failure, repeated creation/destruction, orderly shutdown, and rendezvous/Gloo path used by application. Do not accept silent fallback to legacy TCPStore. Use bounded stress and Windows memory instrumentation if available to check the formerly affected boundary.
5. Run applicable upstream CPU/distributed tests, project integration and actual tensor/embedding/application consumers, restart/recovery and exceptional shutdown tests. Compare semantic baseline and performance/resource changes using declared input budgets. Audit Python plus native artifacts, dependency provenance and runtime load paths. Independent review must bind results to final hashes. A passing import or uv_loop_size call alone is insufficient.

Rollback: candidate remains side-by-side; switch only a dedicated test launcher/environment. If future production activation is separately authorized, use reversible environment/launcher selection with original locked wheel and uv.dll intact. Never overwrite system DLLs or the active venv during MVP. Close candidate processes before rollback; verify original hashes and baseline smoke in a fresh process. Do not unload/swap a DLL within a live Python process. No activation or rollback has been performed.
